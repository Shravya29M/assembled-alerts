# Design Decisions

Each entry: decision — one-line reasoning.

1. **Hand-replayed oracle is provisional.** The 20-notification list in PLAN §7.1 is frozen only after the engine reproduces it and differences are inspected. — A hand replay can contain arithmetic or ordering mistakes, so neither it nor the engine is trusted alone.
2. **Observation horizon is inclusive (≤ 10:30).** — a_23's long-call deadline is exactly 10:30, and the last observation covers that instant.
3. **A timer with deadline D fires only once an accepted event with ts > D arrives, or at end of input.** — File-order replay cannot know all events at D have been seen until a later timestamp appears. This guarantees a same-timestamp ending event always cancels its timer, whatever its position in the file.
4. **emitted_at for timers is the clock at the firing step; effective_at is the deadline.** — This makes the replay lag visible (for example, a_11 is effective 09:55 and emitted 10:00) instead of claiming a notification went out before the engine could know it.
5. **Duplicate, stale and invalid events never advance the clock or trigger timers.** — Rejected input must have no side effects, or dedupe and freshness would not really be protections.
6. **a_23 conflicting activity is a diagnostic, not a state override.** — agent_state_change is the authoritative call-state source; adherence's actual_state is secondary evidence.
7. **Freshness is also tested with a synthetic stale event that would alert.** — The dataset's stale VIP snapshot would not alert even if accepted, so it cannot prove freshness protection works.

## Phase 1 — schema and parsing

8. **Python 3.12 via a uv-managed interpreter in `.venv`.** — CLAUDE.md requires 3.12; the system `python3` is 3.14, and uv already has CPython 3.12.14 installed.
9. **Parsing and validation live in Phase 1; dedupe, freshness, the simulated clock and state live in Phase 2.** — The schema must be checked against real data before the engine is built on it.
10. **Agent states are a fixed set: available, on_call, on_break, in_meeting.** — Verified against every previous_state, new_state, scheduled_state and actual_state value in the dataset; a fixed set catches typos. A production system might map unknown states to "other" so a new state label does not drop real transitions.
11. **Unknown extra fields are rejected.** — The dataset is fixed, so an unexpected field means we misunderstood the data. A production system would usually ignore and log unknown fields and version its schema (additive changes, a schema registry), so producers can evolve without breaking consumers.
12. **Strict types: no silent coercion (for example "18" → 18 or 1 → true).** — Coercion would let malformed data pass as valid.
13. **Timestamps must be timezone-aware and are normalized to UTC; naive timestamps are rejected.** — Comparing naive and aware datetimes is a classic bug, and all rule logic assumes one timezone.
14. **null and [] stay distinct and are never replaced with invented values.** Nullable fields: queue_ids (both agent event types), volume_forecast_next_15m, violation_started_at, previous_state, previous_state_duration_sec. — PLAN §3 forbids converting missing data to zero or empty.
15. **The source line number is stored next to the event, not inside it; event_id, ts and line number stay separate.** — They serve different jobs: event_id for dedupe, ts for the clock, line number for file order and diagnostics.
16. **A malformed line is recorded as rejected, with its line number and a readable reason, and loading continues. Phase 1 does not reject duplicates or stale lines.** — One bad record should not hide the rest, and duplicate or stale handling is engine policy (Phase 2).
17. **Blank or whitespace-only lines are rejected with reason "blank line", not skipped.** — Nothing in the input disappears silently; the trailing newline at end of file is not a line.
18. **agent_id (both agent event types) and queue_id (queue_snapshot) must be non-empty, as event_id must.** — Routing and state keys depend on them; an empty ID cannot be attributed to an owner.
19. **No pairing constraint between previous_state and previous_state_duration_sec.** — In the dataset they are always both null (8 first-seen events) or both set, but that is an observed pattern, not a documented schema rule; nulls are preserved as-is.
20. **Nullable fields are still required keys: the key must be present, and its value may be null.** — Keeps "the source said unknown" (null) distinct from "the source omitted it" (missing key), matches the exact key set enforced by `extra="forbid"`, and all 96 dataset records include every key for their type.

## Phase 2 — engine state and rule evaluation

21. **Dedupe on event_id runs before freshness; an ID is marked seen even if its event is stale. A duplicate with a differing payload is flagged `duplicate_payload_differs`; the first version wins.** — Repeated stale events are reported consistently, and line 95 really does differ from line 50.
22. **Freshness is per (event family, subject); equal timestamps are fresh and the later line wins.** — Queue metrics, call state and adherence are separate evidence streams, and same-timestamp events are legitimate (Decision 3 relies on them).
23. **The clock advances only on accepted events and never rewinds; late-but-fresh events are accepted.** — A late event for one subject is still valid evidence, but it cannot move time backwards for everyone else.
24. **Each fact has one authoritative event family; disagreements become diagnostics, never cross-family writes. `conflicting_activity` is recorded only when a call state is known.** — Generalizes Decision 6; "unknown" is not a conflict.
25. **A repeated state (for example on_call → on_call) is not a transition.** — The call episode start and `since` stay put, so deadlines and duration checks stay honest.
26. **Duration mismatch is derived from accepted transitions; the reported duration is a diagnostic only, and first-seen agents are not checked.** — Timers trust observed transitions, not source claims (a_31: 3900 reported vs 3300 derived).
27. **The effective adherence start is the reported start if it is not after the check, otherwise the check's ts; it is fixed for the whole run. `adherence_start_changed` compares the source's own non-null reports (`AdherenceState.reported_start`).** — The deadline never moves, and a fallback start is not mistaken for a changed report.
28. **The signature is `evaluate(rule, subject_state, clock) -> Decision`: a clock, not an event.** — A timer check has a clock but no triggering event; this reconciles the CLAUDE.md and PLAN §6 wordings.
29. **SLA ratios strictly between resolve and warning return `hold` (implemented). Planned for Phase 3, not yet implemented: never open or resolve an incident on `hold`, and silently downgrade an open critical to warning.** — Hysteresis prevents flapping, and calling 93/120 "critical" would be false.
30. **SLA thresholds are ratios of the per-snapshot target, compared by division, and must be finite.** — Targets differ per queue (120 s vs 300 s); division keeps exact boundaries like 90/120 = 0.75; an infinite ratio would silently disable a severity.
31. **Rule configs are strict, frozen Pydantic models with configurable thresholds (PLAN §4 defaults) and cross-field validators; an invalid config fails at creation.** — Configurability is P0, and a bad config must never surface mid-replay.
32. **Scope is required and validated, and its kind must match the rule (queue rules take queues, agent rules take agents). Phase 3 will resolve it to subjects.** — Every rule states what it covers; "all_owned" needs the ownership map, which is Phase 3.
33. **`evaluate` receives `enabled` but deliberately ignores it (implemented). Planned for Phase 3, not yet implemented: skip disabled rules, close their open incidents as `disabled`, cancel their timers, and on re-enable use effective_at = max(due_at, enabled_at).** — Returning `clear` for a disabled rule would masquerade as recovery.
34. **Duration conditions are inclusive: `met` when clock ≥ due_at (implemented). Planned for Phase 3, not yet implemented: a timer fires only when the next accepted event has ts > D, or at end of input (Decision 3).** — The condition and the firing policy are separate concerns.
35. **Late events: durations are measured from event timestamps, and "now" is always the replay clock.** — Prevents both early and backdated alerts; the PLAN §6 emitted_at wording for late events is to be fixed in Phase 3.
36. **Dedupe, freshness and the clock live in `state.py`, not `ingest.py` (PLAN §8 updated).** — Keeps structural validation separate from engine policy, as approved in Phase 1.

## Phase 3 — incidents, timers, routing and persistence (design approved; not yet implemented)

37. **`ReplayState.check(sourced)` is a side-effect-free acceptance check that `apply` reuses; the engine fires timers only before an event that will be accepted.** — Timers must fire before the triggering event is applied (an exit at 10:15:30 must not cancel a 10:15 timer first), while duplicates and stale events must never trigger them.
38. **Pending duration conditions exist only as timers; an incident is created when its timer fires.** — Otherwise every short call would create and cancel an incident nobody was notified about.
39. **Long-call and adherence incidents have severity None.** — Duration rules have no warning/critical levels; inventing one would mislead.
40. **Every rule has a required `recipient` (a known lead). Eight rules are seeded: four templates × two leads, scope `all_owned`, with rule IDs such as `backlog.lead_billing`.** — PLAN §1 has leads choose recipients; rule-ID order puts backlog before SLA within one event, as in PLAN §7.1.
41. **Explicit scopes must name known subjects; a subject the recipient does not own requires `cross_owner: true`. Routing is validated when a rule is added or edited.** — Cross-owner targeting must be deliberate, never a typo or an accident.
42. **A subject missing from the ownership map gets one `unowned_subject` diagnostic; no recipient is guessed and no notification is sent.** — PLAN §9: unknown ownership is diagnosed, not guessed.
43. **A timer with deadline D fires only when an accepted event makes the clock exceed D, or at end of input if D ≤ horizon. Exception: a timer created by a late-but-fresh event with D < clock fires right after that event, with effective_at = D.** — Refines Decision 3 for late events, where evidence beyond D has already been seen.
44. **For immediate rules, effective_at is the triggering event's ts and emitted_at is the clock; they differ only for late-but-fresh events.** — Corrects the PLAN §6 wording, which assumed both always equal the event ts.
45. **Rule edits never emit notifications and never rewrite history. Queue rules use the new thresholds at the queue's next snapshot. Duration timers are recomputed at the edit, with deadline max(due, edit time), and fire under Decision 43. An ACTIVE duration incident ends only when its episode ends; a `pending` result while it is ACTIVE is ignored.** — Implements PLAN §4 "edits apply on the next evaluation"; a threshold change is not evidence that a call ended.
46. **Disabling a rule closes its open incidents as `disabled` (no notification) and cancels its timers; re-enabling works like an edit.** — PLAN §5; disable is not recovery.
47. **Each notification records the `rule_version` it was produced under.** — Shows which thresholds produced it after edits.
48. **Incident IDs are deterministic: `{rule_id}:{subject_id}:{n}`, where n counts incidents for that pair in replay order; notification IDs are global sequence numbers in emitted order.** — Replay rebuilds identical IDs; no random UUIDs or wall-clock values.
49. **Persistence is an append-only journal of every input (events with their outcomes, and rule changes with full configs and versions) in order, plus stored incidents and notifications. Recovery replays the journal and checks that the rebuilt outputs equal the stored ones.** — The engine is deterministic, so its state follows from its inputs; replaying with only the latest rules would not reproduce edits or disables.
50. **SQLite is the source of truth: each step is written in one transaction; if the write fails, the transaction rolls back and the in-memory engine is rebuilt from the journal.** — Memory can never get ahead of the database, and recovery is the only rebuild mechanism.
51. **The PLAN §7.1 oracle is copied verbatim into a test fixture before implementation. A mismatch is investigated row by row against the source lines; fixing either side needs approval and an engineering-log entry, and expected rows are never tuned to match.** — The hand replay predates the engine (baseline commit 987b34f), so it is an independent check.

## Phase 3 — checkpoint 3.1 (implemented: timers, incidents, basic routing, engine)

52. **Late evidence that contradicts a fired alert never rewrites history. The resolution keeps the late event's ts as effective_at, even if that is before the incident's opened_at, and the engine records `alert_contradicted_by_late_evidence`.** — Notifications are an immutable record of what was sent; the diagnostic makes the contradiction visible instead of hiding it.
53. **Resolution notifications carry the incident's last severity.** — PLAN §7.1 is silent; "billing SLA resolved (was critical)" is more useful to a lead than a blank.
54. **A timer notification's line_number is the line whose arrival fired it; end-of-input notifications have None.** — It points to the evidence that made the alert certain, and no line exists at end of input.
55. **Every rule change (edit, disable, enable) increments its version; `reset()` clears replay state but keeps the current rules and versions, and does not restore factory defaults. The SQLite store must behave the same way.** — Reset means "replay again with what is configured", not "undo configuration".
56. **A duration `met` at exactly clock == D does not open an incident; the timer stays live and fires under Decision 43.** — Other same-ts events could still end the condition (dataset line 57: a_19 is checked at 09:45 = D, and the alert fires at line 64, 09:48).
57. **The engine calls `pop_due` twice per accepted event: before applying it (normal firing) and after evaluating rules (timers that a late event just created with D < clock).** — One queue handles both cases; only timers created in this step can be due on the second pass.
58. **A repeated observation with an unchanged deadline does not reschedule its timer.** — Rescheduling would change its creation sequence, and with it the tie-break order for equal deadlines.

## Phase 3 — checkpoint 3.2 (in progress)

59. **Active incidents are looked up by (rule_id, subject_id), without recipient.** — PLAN §5 allows one active incident per rule × subject; with the recipient in the key, a recipient edit opened a second incident (reproduced for both queue and duration rules).
60. **Editing a rule's recipient while an incident is ACTIVE keeps the same incident ID and lifecycle and updates the incident's current recipient. The edit sends no notification, history is unchanged, and later escalations and resolutions go to the new recipient.** — The condition did not change, only who is responsible for it.
61. **A subject with no seeded owner gets one `unowned_subject` diagnostic per replay, on its first accepted event, and is never notified.** — Implements Decision 42; `reset()` clears the record together with the other replay state.
62. **Planned: `finish()` finalizes the replay; `step()` is rejected until `reset()`.** — After end of input the strict-deadline guarantee no longer holds (a same-ts exit could arrive after its timer fired at the horizon).
63. **`disable_rule` and `enable_rule` are `update_rule` with `enabled` flipped; every change goes through routing validation, bumps the version and reconciles incidents and timers in one place.** — One code path cannot drift out of sync with itself.
64. **When an edit stops covering a subject (rule disabled or subject out of scope), its ACTIVE incident closes as `disabled` with closed_at = the replay clock, its timer is cancelled, and nothing is notified. No reason field is stored.** — The rule stopped watching, so this is not a recovery; a reason field would add a schema change for no current consumer.
65. **For an `all_owned` rule, a recipient change is also a scope change: subjects that leave are closed as `disabled`, subjects that stay keep their incident (Decision 60), and newly covered duration subjects get timers recomputed from current state.** — Ownership defines what `all_owned` covers.
66. **Implements Decision 62. After `finish()`, `step()` raises `ReplayFinishedError`, and a repeated `finish()` returns []. Edits are still allowed: they update config and version, and they still close or reassign existing incidents, but they never schedule timers or create incidents and notifications. `reset()` clears the flag.** — A finalized replay's output cannot grow, but "a disabled rule has no ACTIVE incidents" stays true.
67. **`Engine(rules)` rejects duplicate rule_ids with ValueError; `cross_owner=True` is allowed even when the recipient owns every listed subject.** — Silently keeping the last duplicate hides a config error; a redundant flag is harmless.
68. **After `finish()`, a duration-rule edit only moves or cancels that rule's existing timers. A timer moves if its new deadline is strictly after the final clock; otherwise it is cancelled, with no incident or notification. Subjects without a timer never get one, and nothing fires until `reset()`.** — Pending timers stay consistent with the finalized config without the finished replay producing new output (refines Decision 66).
69. **The engine re-runs full Pydantic validation (`model_validate(rule.model_dump())`) on every rule it receives, at construction and in `update_rule`, before any state changes.** — `model_copy(update=...)` and `model_construct` skip validation, so an invalid rule could otherwise reach the engine.

## Phase 3 — checkpoint 3.3 (SQLite journal and recovery)

70. **Four tables: `baseline_rules` (configs and versions at the start of the current replay), `journal`, `incidents` and `notifications`. `reset()` clears the journal and outputs and stores the current rules and versions as the new baseline.** — Recovery must start from the rules in force at the last reset, not from factory defaults or version 1 (Decision 55). PLAN §8's `operational_state` and `processed_events` tables are derived from the journal (Decision 49).
71. **The journal has three kinds of row: `event` (including duplicate and stale events, with their outcome), `rule_change` (full validated config and resulting version; disable and enable are rule changes with `enabled` flipped) and `finish` (the first call only). Rejected operations are not journaled.** — Replaying duplicates reproduces their diagnostics; an invalid edit or a step after finish changes nothing, so there is nothing to replay.
72. **Each operation first runs pre-checks with no side effects (`step` after `finish()`, and rule edits via `Engine.validate_rule`). Their errors are re-raised without a rebuild. Then the engine mutation and one transaction (journal row, changed incidents, new notifications) follow. Any error from the mutation, of any type, or a failed write rolls back and rebuilds the engine from the database. If the rebuild fails, the Store refuses every operation until it is reopened.** — Whether a rebuild is needed depends on where the error happened, not on its type: only the pre-checks are guaranteed to change nothing.
73. **Recovery replays the baseline and journal, then checks every journal outcome and rule version, and checks the stored notifications and incidents (order and all fields) against the replay; any difference raises `RecoveryMismatchError`. The clock, timers, diagnostics and finished state are rebuilt, not stored. Recovery delivers nothing and no code reads the wall clock.** — Stored outputs are a check on the journal, and replay is deterministic.
74. **`Engine` gains `versions=` (to restore a baseline), a read-only `finished` property and a side-effect-free `validate_rule()` that `update_rule` reuses. `Store.engine` returns a deep-copied snapshot for inspection; Store methods are the only supported way to change persistent state. Known limitation: a failed `create()` can leave an empty SQLite file, which a later `create()` refuses.** — These are the minimal additions recovery needs; a copy means outside code cannot bypass the journal.
